# Recruiter-Na v0.2.3

日期：2026-10-29。源码分支 `release/v0.2.3`，tag `v0.2.3`，工作流合同仍为 5.0.2。

## 问题与修复

此前展示测试使用了明确配置的合成 JSONL，后续部署沿用了该 staging 环境文件；不是升级把虚拟简历写入真实 MySQL。本次恢复实例原有 MySQL 配置，禁止 JSON 开发回退，真实原件根目录采用既有受限目录。所有凭据仅在服务器保存。

保留当前九条需求、owner 和 JD，将七份包含合成候选的推荐快照作废并保留审计；有 JD 的需求回到可重新筛选状态，暂停需求仍暂停。原工单库、原环境与合成运行数据隔离备份，不再进入当前候选池。历史旧库保留，不未经授权合并或重写其他历史需求。

真实回复检查发现待核实项暴露 RL 编号。现在从已批准 red_lines 顺序映射业务说明，未知映射显示“资格限制条件”；不改规则、事实、资格判断、推荐排序或 Policy。继承 #5/#6/#7 的既有修复。

## 验证边界

- 原连接通过 ResumeRepository 验证：112 份真实 MySQL 简历；限定检索三名检验相关候选，均为真实来源且原件可读取，不浏览或输出全库个人资料。
- 实际模型六人试跑：四人完成评估并可推荐，首批三人回复已检查；两人为模型 JSON 格式/契约失败，保持技术失败，不当作不合格淘汰。未发送钉钉业务消息、联系候选或写入生产 MySQL。该试跑不代表业务验收，也不是全库评估。
- 本地公开合同回归 124 passed，IM 12 passed，编译/密钥/差异检查通过。完整本地 536 passed / 相同八项既有失败 / 10 skipped，相比主分支新增两项通过、无新增失败。
- 新增两项先失败后通过回归，覆盖业务标签映射与无映射兼容。公开 CI 仅运行不依赖私有材料的合同/IM/编译/密钥检查，不伪装完整私有集成。
- 完整本地测试使用与 #6 相同材料和环境对照；未提供的私有简历来源、画像/JD 库和 OCR 环境导致的八项既有失败，完整名称见 [#6 验证记录](../reviews/pr6-compatibility.md)。不修改 Policy 或伪造资料使它们变绿。

## 部署与实际验收

发布独立版本目录，复用已验证依赖、受限真实数据根目录和持久工单库；环境文件显式固定 MySQL，禁止重新引用 synthetic-resumes。切换前备份工单和服务覆盖配置，回滚不自动覆盖新产生的工单。仅重启招聘娜，核对同机 PulseHR PID/状态不变。

部署回执保存在服务器及本地私有运行记录，不将真实候选、模型原始输出或凭据写入源码/Release。用户可继续原需求并发送“开始筛选”；旧虚拟推荐已作废，需重新筛选才能看到真实候选。用户负责真实业务验收。
