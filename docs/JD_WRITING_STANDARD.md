# 对外发布 JD 撰写规范（AI 生成可复用版）

本文件把一份成熟招聘工具「AI 生成 JD」的思考过程提炼成可执行规则，并说明它在本仓库
`runtime/rn/resume_screening/jd/` 中的落地方式。目标是：无论人写还是模型写，产出的 JD
都满足同一套结构与合规约束，且可以被机器自检（`cli jd --check`）。

## 1. 输出结构：固定三个板块

对外发布的 JD 只有三个内容板块，顺序固定：

1. **职位名称**（一级标题）
2. **岗位职责**
3. **任职要求**（按 KSAO 分四行：学历专业 / 知识技能 / 证书经验 / 职业素养）
4. **加分项**（可选，没有就不写）

内部管理用的信息（部门、紧急程度、到岗时间、岗位定位、JD 模板编号）不进对外版。
对外版只保留：工作地点（去公司/园区标识）、招聘人数、薪资范围、工作模式、用工性质。

**两层结构**：JD 与匹配标签是两层，不要合并。

```
标准画像 + 本次实际需求  ──cli jd──▶  jd.md（职位名称 / 岗位职责 / 任职要求：学历·专业·经验·证书·技能与能力·职业素养）
                                              │
                                              └──cli jd --tags──▶  jd.tags.md（匹配标签（取自 JD）：能力/经验计分、特质不生成标签、硬性条件单独核验）
```

`jd.md` 的任职要求保留 JD 自己的措辞（含「技能与能力」组）；匹配标签是从该 JD 的任职要求与关键能力
派生出来的筛选视图，只出现在 `jd.tags.md` 里，**不写回 JD**，也不对外发布。匹配标签只收能力/经验两类——
**特质不生成标签**（JD 的「职业素养」仍留在可发布 JD 的任职要求里，作面试参考，不进命中率）。
聊天呈现顺序固定为：JD 正文 → 匹配标签（取自 JD） → 候选人匹配结果。

**最后呈现（交付成稿）**：`cli jd --presentation` 把两层合成 `jd.presentation.md`，固定三个大项——
`## 岗位职责`、`## 任职要求`（「加分项」折入其中）、`## 匹配标签（取自 JD：<岗位>…）`。匹配标签节
**只列实际参与评分的标签名**（一行能力、一行经验；直接复用 `requirements_from_jd` 的结果，成稿与命中率
同一套标签，不用画像 `key_abilities`/`key_experiences` 原文），不放表格、判据、命中线索、特质或硬性条件——
这些细节留在 `jd.tags.md`。标签名必须是短标签（词表名或压缩到 ≤12 字的短语），不能整句职责直接当标签名。
聊天里直接贴这三个大项；对外发布仍然用 `jd.md`（两节，不含匹配标签）。

交付硬规则：回复必须贴出 JD 正文（`jd.presentation.md` 全文，或至少 `## 岗位职责` 与 `## 任职要求`），
只给文件路径、需求确认摘要或需求条目复述都不算交付；复用已有 JD 时也要重新读文件再贴。



## 2. 职位名称：行业通用称谓

- 用行业通行的岗位名，例如「医学检验技术员」「检验技师」「PCR 实验员」。
- 不出现公司名、集团名、园区名、内部组织名（如「迪安」「集团总部」「XX 中心」）。
- 不出现职级、性别、年龄、地域限定词，除非该岗位依法必须有执业地点要求。
- 代码入口：`jd.generator.sanitize_title()`；自检错误码 `title_company`。

## 3. 岗位职责：强动词 + 标准长度 + 业务流程排序

- **条数**：5–7 条（少于 5 条信息不足，多于 7 条重点涣散）。
- **每条 15–30 字**（含标点，按中文 WORD 字数口径）。
- **强动词开头**：负责 / 执行 / 完成 / 操作 / 维护 / 校准 / 复核 / 记录 / 上报 / 整理 / 归档 / 处置 …
  不要用「按照…」「根据…」「在…指导下」这类状语开头（自检错误码 `duty_weak_verb`）。
- **按业务流程排序**，不要按重要性或时间随机排。以检验技术员为例：
  1. 样本接收、编号、离心、分装与保存
  2. 常规检验项目检测与结果复核
  3. 仪器日常操作、校准、维护与故障报修
  4. 室内质控、室间质评与异常结果上报
  5. 检验报告录入、审核、发放与归档
  6. 生物安全、医疗废物与消毒规范执行
- 职责里写「做什么、做到什么标准」，不写任职资格（学历/证书放到任职要求）。

## 4. 任职要求：按 KSAO 四维组织

- **条数**：5–7 条，覆盖四个维度（自检 `requirement_count_low/high`、`ksao_missing`）。
  - **学历专业**：学历层次 + 可接受专业范围。
  - **知识技能**：专业理论知识、仪器/方法/系统操作能力。
  - **证书经验**：执业/资格证、实习或工作年限、行业经历。
  - **职业素养**：责任心、细致严谨、沟通协作、抗压与轮班适应等。
- 每条一个维度，不要把「学历 + 证书 + 经验」塞进一句话。
- 应届可接受的条件要写清边界（如「应届生可接受已报名待考」），避免把合格候选人误筛掉。
- **只写需求方提出的条件**：岗位画像继承来的能力/经验（如「快速学习能力」「规范操作与执行能力」
  「检验科经验」）是匹配标签的素材，不是 JD 的任职要求；它们只出现在 `jd.tags.md`，不能变成
  `jd.md` 的任职要求条目。

## 5. 篇幅与文风

- 对外版全文 **400–600 字**（含标点与序号，按 WORD 字数口径；自检 `length_low/length_high`）。
- 用陈述句、动宾结构；不写营销话术、不写感叹号、不写「我们提供…」式雇主广告。
- 数字与单位统一（如「3.5–4K/月」），时间与轮班写清频次。

## 6. 合规：零企业信息、零敏感词

- **企业信息**：不出现公司/集团/园区/内部系统名（默认词表：迪安诊断、迪安、集团总部、本公司、我司、本企业；
  可用环境变量 `JD_FORBIDDEN_COMPANY_TERMS` 覆盖）。自检错误码 `company_info`。
- **敏感词**：不出现性别、婚育、年龄、籍贯、民族、户籍、身份证、政治面貌、宗教等歧视性条件。
  自检错误码 `sensitive_terms`；年龄数字形如「25-35 岁」也会被识别。
- 内部版允许保留这些条件用于筛选判定，但**对外版必须删除**；`--external` 渲染会自动删除
  「其他硬性条件」里的敏感值，并在报告里给一条 `sensitive_terms_dropped` 警告，避免悄悄消失。

## 7. 自检（机器可执行）

```powershell
# 生成对外版并自检，报告写到 jd.quality.md
python -m rn.resume_screening.cli jd --fields-file <fields.json> --external --check --out <dir> --overwrite
```

检查项与判定：

| 检查 | 通过条件 | 不通过 |
| --- | --- | --- |
| 三模块标题 | 职位名 + 岗位职责 + 任职要求 | `title_missing` / `duties_section_missing` / `requirements_section_missing` |
| 职位名合规 | 无公司词 | `title_company`（ERROR） |
| 职责条数 | 5–7 | `duty_count_low/high` |
| 职责长度 | 每条 15–30 字 | `duty_length` |
| 职责动词 | 强动词开头 | `duty_weak_verb`（ERROR） |
| 职责来源 | 本次需求提供 | `duties_from_template`（WARN，发布前需用人部门确认） |
| 任职要求条数 | 5–7 | `requirement_count_low/high` |
| KSAO 覆盖 | 四个维度都有 | `ksao_missing` |
| 篇幅 | 400–600 字 | `length_low`（ERROR）/ `length_high`（WARN） |
| 合规 | 无企业信息/敏感词 | `company_info` / `sensitive_terms`（对外版为 ERROR） |

- 有 ERROR 时命令退出码为 `4`（`EXIT_QUALITY_ERROR`），报告仍会写盘。
- 内部版（不加 `--external`）的合规问题降级为 WARN，方便先看清问题再改。

## 8. 生成方式：确定性生成 + 可选 LLM 起草

1. **确定性生成（默认）**：从需求字段 + 标准岗位画像 + 同岗位模板拼装，结果可复现、不依赖外部服务。
   若本次需求没给职责，会引用同岗位模板的职责措辞，并在文中标注「发布前需用人部门确认」。
2. **LLM 起草（`--draft`）**：把本规范写进 prompt，让模型只输出 JSON
   `{title, responsibilities[], requirements[{label,text}], bonus_points[]}`，再并入同一套渲染与自检。
   需要 `RECRUITER_LLM_API_KEY` / `RECRUITER_LLM_BASE_URL` / `RECRUITER_LLM_MODEL`；不可用或输出不合规时
   自动回退确定性生成，stdout 正常产出，stderr 给出原因。
3. 无论哪种方式，**发布前一律跑 `--check`**；模板措辞、LLM 起草都属于「草稿」，人工确认后才算定稿。
